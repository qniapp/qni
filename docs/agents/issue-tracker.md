# Issue tracker: GitHub

Issues and specs live in GitHub repository `qniapp/qni`. Use the `gh` CLI. Prefer explicit
`--repo qniapp/qni` on commands rather than inferring the repository from worktrees or remotes.
For `gh api`, use the explicit `repos/qniapp/qni/` path.

## Conventions

- Create: `gh issue create --repo qniapp/qni --title "..." --body-file -`. Supply multiline
  bodies through a heredoc.
- Read: `gh issue view <number> --repo qniapp/qni --comments`. Fetch labels with
  `--json number,title,body,labels,comments`; filter comments with `--jq` as needed.
- List: `gh issue list --repo qniapp/qni --state open --json number,title,body,labels,comments`.
  Use `--label`, `--state`, and `--jq` to narrow results.
- Comment: `gh issue comment <number> --repo qniapp/qni --body-file -`.
- Apply or remove labels: `gh issue edit <number> --repo qniapp/qni --add-label "..."`
  or `--remove-label "..."`. Use the role mapping in [triage-labels.md](triage-labels.md).
- Close: `gh issue close <number> --repo qniapp/qni --comment "..."`.

Every issue body or comment posted during triage, including closing comments, must start with
this exact first line:

```text
> *This was generated by AI during triage.*
```

## Pull requests as a triage surface

**PRs as a request surface: no.** External PRs are not part of the issue triage queue.

GitHub shares issue and PR numbers. For an ambiguous `#<number>`, resolve with
`gh pr view <number> --repo qniapp/qni`, falling back to `gh issue view <number> --repo qniapp/qni`.

## Skill operations

When a skill says "publish to the issue tracker", create a GitHub issue. When it says
"fetch the relevant ticket", run `gh issue view <number> --repo qniapp/qni --comments`.

## Wayfinding operations

For `/wayfinder`, the map is one issue with child issues as tickets:

- Map: label it `wayfinder:map`; keep Notes, Decisions-so-far, and Fog in its body.
- Children: link tickets using GitHub sub-issues via `gh api` when available. Otherwise use
  a task list in the map and a `Part of #<map>` line in each child. Use `wayfinder:<type>`
  labels (`research`, `prototype`, `grilling`, or `task`). Keep the triage disclaimer first
  when these bodies are posted during triage.
- Blocking: use native issue dependencies when available:
  `gh api --method POST repos/qniapp/qni/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`.
  Get the database ID with `gh api repos/qniapp/qni/issues/<number> --jq .id`, not the issue
  number or node ID. Otherwise record `Blocked by: #<number>` lines near the top of the child.
- Frontier: inspect the map's open children in map order. Skip assigned tickets and those with
  open blockers (`issue_dependencies_summary.blocked_by > 0`, or open issues in `Blocked by`
  lines). The first remaining ticket wins.
- Claim: the session's first write is `gh issue edit <number> --repo qniapp/qni --add-assignee @me`.
- Resolve: comment with the answer, close the child, then append a summary and link to the map's
  Decisions-so-far. A child is unblocked when all its blockers are closed.
